# Grill-Me Session: Replace Chevrotain with Tree-sitter
**Date:** 2026-05-02  
**Based on:** docs/requirements.md

---

## Context

The requirements call for replacing Chevrotain with tree-sitter in Langium for incremental parsing and performance. The codebase has Chevrotain deeply embedded across 19+ files. Key pipeline: `TokenBuilder` → `Lexer` → `LangiumParser` (wrapping `ChevrotainWrapper` → `EmbeddedActionsParser`) → `CstNodeBuilder` → AST via assignments → `Linker` for cross-refs.

---

## Q1: What is the integration boundary for tree-sitter?

**Options:**
- **A (Shallow):** Use tree-sitter only as parser/lexer, translate output into existing Langium `CstNode`/AST types, keep rest of Langium untouched.
- **B (Deep):** Use tree-sitter's native node types directly, eliminate `CstNodeBuilder` and `CstNode` hierarchy entirely.

**Recommendation:** Option B, but phased — start with a compatibility shim, remove in v2.

**Decision: Option B — full CST elimination, not phased.**

---

## Q2: How do we generate tree-sitter grammars from Langium's `.langium` grammar files?

**Options:**
- **A (Code generation):** Write a Langium grammar → `grammar.js` compiler from the start.
- **B (Manual grammar.js):** Hand-write `grammar.js` for v1 arithmetic example, defer auto-generation.

**Recommendation:** Option B for v1, design mapping layer generically.

**Decision: Option A — Langium→tree-sitter grammar compiler from the start. Thoroughly research all semantic actions that can't be mapped.**

## Mapping Analysis (researched before Q3)

### Directly mappable
| Langium construct | Tree-sitter equivalent |
|---|---|
| `Alternatives` (`\|`) | `choice()` |
| `Group` (sequence) | `seq()` |
| `cardinality ?` | `optional()` |
| `cardinality *` | `repeat()` |
| `cardinality +` | `repeat1()` |
| `Keyword` | string literal |
| `TerminalRule` (non-hidden) | named rule |
| `TerminalRule` (hidden) | `extras` array |
| `TerminalRule fragment` | `_`-prefixed inline rule |
| `ParserRule fragment` | `_`-prefixed inline rule |
| `InfixRule` with precedence | `prec.left()` / `prec.right()` |
| `CharacterRange` | regex character class |
| `RegexToken` | regex pattern |
| `Wildcard` (`.`) | `.` in regex |
| `entry` marker | first rule (tree-sitter convention) |

### Cannot be mapped — require post-parse reconstruction
| Langium construct | Why it breaks | Proposed handling |
|---|---|---|
| `Assignment` (`=`, `+=`, `?=`) | No semantic actions | `field()` naming + post-parse operator semantics |
| `Action` (`{Type}`, `{infer T}`) | Mid-rule type switching impossible | Post-parse mapper uses grammar metadata |
| `CrossReference` (`[TypeName:T]`) | Purely semantic | Post-parse mapper records raw text; linker resolves |
| `DataType` rules | Tree-sitter always produces nodes | Post-parse mapper converts leaf text to primitives |
| `GuardCondition` (`<param>`) | No parameterized/conditional rules | Expand at compile time |
| `RuleParameter` | Same | Expand at compile time |
| `UnorderedGroup` (`&`) | No concept in tree-sitter | Expand to permutations / drop |
| `SemanticPredicate` (`=>`) | No equivalent | Drop or external scanner |
| `NegatedToken` (`!element`) | Not directly expressible | External scanner / drop |
| `UntilToken` (`->element`) | Not directly expressible | External scanner / drop |
| Lookahead assertions (`?=`, `?!`) | No direct equivalent | External scanner / drop |

### New tree-sitter concepts Langium grammar must express
| Feature | Purpose |
|---|---|
| `conflicts` | GLR disambiguation |
| `prec(n)` | Non-infix precedence |
| `externals` | External C scanner tokens |
| `word` rule | Keyword disambiguation |
| `supertypes` | LSP node grouping |

## Q3: How does the post-parse AST mapper work — where does grammar metadata live at runtime?

**Example grammar:**
```langium
grammar Arithmetic

entry Program:
    statements+=Statement*;

VarDecl:
    'var' name=ID '=' value=Expression ';';

Expression:
    Multiplication ({infer BinaryExpr.left=current} op=('+' | '-') right=Multiplication)*;

Primary:
    {infer NumberLit} value=INT
  | {infer VarRef} ref=[VarDecl:ID];

terminal INT: /[0-9]+/;
terminal ID: /[a-zA-Z_][a-zA-Z0-9_]*/;
hidden terminal WS: /\s+/;
```

For `var x = 1 + 2;`, tree-sitter produces:
```
program
  var_decl
    ID "x"
    expression
      primary → INT "1"
      "+"
      primary → INT "2"
```

Target Langium AST:
```ts
{
  $type: 'Program',
  statements: [{ $type: 'VarDecl', name: 'x',
    value: { $type: 'BinaryExpr',
      left: { $type: 'NumberLit', value: 1 },
      op: '+',
      right: { $type: 'NumberLit', value: 2 } } }]
}
```

**Options:**
- **A (Metadata table):** Compiler emits `grammar.js` + `mapping.ts`. One generic mapper for all languages consults the table.
- **B (Generated mapper):** Compiler emits a per-language TypeScript mapper class. No runtime metadata table.

**Recommendation:** Option A — metadata table keeps mapper logic testable and language-agnostic.

**Decision: Option A.**

## Q4: What do we do with `UnorderedGroup` (`&`)?

Example: `abstract?='abstract' & static?='static' & visibility=Visibility`

**Options:**
- **A:** Expand to `N!` permutations
- **B:** Compile to `repeat(choice(...))` + post-parse validator
- **C:** Drop entirely

**Recommendation:** Option B for v1.

**Decision: Option C — drop `UnorderedGroup` entirely.**

---

## Q5: How do we handle `RuleParameter` and `GuardCondition`?

Example:
```langium
RuleCall <Predicated>:
    (<Predicated> (predicate='=' | predicate='=>' | predicate='->'))
    rule=[AbstractRule:ID];
```

Only option is compile-time expansion: generate a distinct tree-sitter rule per parameter combination. Parameters are boolean so worst case `2^N` variants.

**Recommendation:** Keep syntax, expand at compile time.

**Decision: Drop `RuleParameter` and `GuardCondition` entirely.**

---

## Q6: tree-sitter binding — native Node.js addon or WASM?

**Options:**
- **`node-tree-sitter`:** Native C++ addon, fast, synchronous. Does not work in browser/web extensions.
- **`web-tree-sitter`:** WASM build, works everywhere. ~10–15% slower. Async init. Each grammar is also a `.wasm` file.

**Recommendation:** `web-tree-sitter` — cross-environment compatibility is non-negotiable.

**Decision: `web-tree-sitter` (WASM).**

---

## Q7: How do we wire tree-sitter's incremental parsing into Langium's document update pipeline?

Tree-sitter stores a `Tree` per document. On edit: `tree.edit(edit)` → `parser.parse(newText, oldTree)`. Unchanged subtrees are pointer-identical.

**Options:**
- **A:** Incremental parse only, full mapper rebuild every update.
- **B:** Incremental parse + incremental AST (patch changed nodes in place).
- **C:** Incremental parse + full AST rebuild + incremental linking (re-link only dirty scopes).

**Recommendation:** Option A for v1, Option C as v2 target. Option B is premature optimization without profiling data showing the mapper is the bottleneck.

**Decision: Option A for v1.**

---

## Interlude: What is a mapper?

The mapper converts tree-sitter's raw syntax tree into Langium's AST. Tree-sitter only knows syntax — it has no concept of `$type`, `+=`, or cross-references. The mapper bridges this gap using the metadata table.

---

## Interlude: Can we get rid of the mapper entirely?

User raised: the mapper still builds a parallel in-memory tree. Can we skip it and work differently for linking and scoping?

**Three strategies explored:**
- **Strategy 1 (tree-sitter nodes as AST):** Use `SyntaxNode` directly everywhere with typed view wrappers. No parallel tree allocated. Problem: all Langium services need rewriting, string-based field access.
- **Strategy 2 (Index-based):** Build flat positional indices after parsing. Linking = hash map lookup. Problem: harder to build incrementally, loses structural info validators need.
- **Strategy 3 (Lazy AST):** Typed interfaces implemented as lazy proxies over tree-sitter nodes. Existing services unchanged. Problem: wrapper infrastructure is largely throwaway work when v2 index-based linker arrives.

**User observation:** If we use lazy wrappers in v1 and index-based in v2, the wrapper code gets thrown away. That's wasted effort.

**Revised recommendation:** Skip lazy wrappers entirely. Build minimal index-based approach from the start. Metadata table is the permanent foundation serving both v1 and v2. For v1, a simple `DocumentIndex` (declarations + references + diagnostics) is sufficient.

**Decision: No mapper, no typed AST, no lazy wrappers. Index-based approach from the start.**

## Q8: Cross-reference resolution with the index-based approach

**8a:** Scope provider walks tree-sitter tree to find declarations → index. Option A (use typed interface) confirmed.

**8b: Incremental cross-reference resolution:**
- **Option A:** Invalidate by position — re-resolve only references in changed ranges.
- **Option B:** Full re-link on every update.

**Recommendation:** Option B for v1, Option A as v2 linker optimization.

**Decision: Full re-link for v1, range-based invalidation for v2.**

- **B:** New `langium treesitter` top-level command.
- **C:** `langium generate` does everything, including invoking tree-sitter CLI to produce `.wasm`.

**Recommendation:** Option B (separate command, keeps old pipeline untouched during transition).

**Decision: Option C — `langium generate` is the tree-sitter pipeline. Chevrotain code is deleted.**

## Q10: How is the `.wasm` file distributed and loaded at runtime?

**10a: Where does `grammar.wasm` live?**
- **A:** Alongside `metadata.ts` in `src/generated/`
- **B:** Dedicated `resources/` directory

**Decision: Option B — `resources/` directory. Binary artifacts should not sit next to TypeScript source.**

**10b: How does the runtime load the `.wasm`?**
- **A (Path-based):** Load via `context.extensionUri`. Works in Node.js and web extensions. Requires `extensionUri` threaded through service container.
- **B (Base64 in metadata.ts):** Encode `.wasm` as base64 string in `metadata.ts`. Works everywhere, no URI needed. Antipattern (binary in TS source).
- **C (Dynamic import):** Bundler handles `.wasm` as asset. Adds bundler config complexity.

**Clarification on "threading through":** `extensionUri` is only available in `activate()`. It must travel through `createLangiumServices()` → `ParserService` → `Language.load()`. This works in web extensions using `context.extensionUri.toString()` (which produces a fetch-able URL) — but `context.extensionPath` (Node.js only) must not be used.

**Decision: Option A — path-based loading via `extensionUri`.**

## Q11: How do we surface parse errors from tree-sitter to LSP diagnostics?

Tree-sitter never fails — it inserts `ERROR` and `MISSING` nodes into the tree.

**11a: Who collects errors?**
- **A:** Dedicated `TreeSitterDiagnosticProvider` — second tree traversal.
- **B:** Index builder collects errors in the same pass.

**Decision: Option B — error collection inside the index builder, one pass.**

**11b: Error message quality?**
- **A:** Generic "Syntax error" messages.
- **B:** Enrich from metadata table ("Expected expression").
- **C:** tree-sitter query patterns per language.

**Decision: Option A for v1 — generic messages. Enrichment in v2.**

## Q13: How does the grammar compiler handle keyword disambiguation (tree-sitter `word` rule)?

Without a `word` declaration, `iffy` would partially match keyword `if`. Tree-sitter's `word` property prevents this.

**Options:**
- **A:** Auto-infer from terminal patterns, `@word` as fallback.
- **B:** Always require explicit `@word` annotation.

**Recommendation:** Option A (auto-infer 95% of cases).

**Decision: Option B — always explicit.**

```langium
@word terminal ID: /[a-zA-Z_][a-zA-Z0-9_]*/;
```

## Q14: What happens to `NegatedToken` and `UntilToken` in terminal rules?

Examples:
```langium
hidden terminal ML_COMMENT: '/*' -> '*/';           // UntilToken
hidden terminal SL_COMMENT: '//' (!('\n'|'\r') .)*; // NegatedToken
terminal STRING: '"' (!'"' .)* '"';                  // NegatedToken
```

**Options:**
- **A:** Compile to regex where possible, error otherwise.
- **B:** Drop both, require explicit regex or `external terminal`.

**Recommendation:** Option B — consistent with clean-break policy.

Migration:
```langium
hidden terminal ML_COMMENT: /\/\*[^*]*\*+([^/*][^*]*\*+)*\//;
hidden terminal SL_COMMENT: /\/\/.*/;
terminal STRING:            /"[^"]*"/;
```

**Decision: Option B — drop both.**

---

## Q15: Drop semantic predicates and terminal lookahead assertions?

- Semantic predicates (`=>`, `->` on grammar elements): no tree-sitter equivalent.
- Terminal lookahead assertions (`?=`, `?!`, `?<=`, `?<!`): no tree-sitter equivalent.

Use `conflicts` and `prec` instead.

**Decision: Drop both.**

---

## Q16: How do language authors declare `conflicts` and `prec` for tree-sitter disambiguation?

**Options:**
- **A:** First-class syntax in `.langium` grammar.
- **B:** Raw tree-sitter `grammar.js` escape hatch embedded in `.langium`.

**Recommendation:** Option A — keeps `.langium` as single source of truth.

```langium
conflicts:
    [Expression, Statement];

ParserRule:
    @prec(2) Alternative1
  | @prec(1) Alternative2;
```

**Decision: Option A — first-class syntax.**
