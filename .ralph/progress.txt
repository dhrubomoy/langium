## Codebase Patterns
- The `treesitter/file-writer.ts` module imports building-block compilers from BOTH `grammar-js-compiler` (parser/terminal/infix/extras/word) AND `metadata-compiler`. When rewriting either to take `ParsedGrammarSet`, the legacy-shim pattern from US-039–US-041 applies: copy the old file to `<name>-legacy.ts`, point `file-writer.ts` at the legacy copy, then replace the original. The legacy file is deleted in US-049 once `composeGrammarJs`/`emitTreeSitterArtifacts` is dropped.
- This is an npm workspaces monorepo. Tree-sitter binary is hoisted to root `node_modules/.bin/tree-sitter` even when declared as devDep of `packages/langium-cli`. Verify with `cd packages/langium-cli && npx tree-sitter --version`.
- Pre-existing test failures: 119 langium-cli tests fail with `Object.groupBy is not a function` because the sandbox runs Node 20.19.4 but `Object.groupBy` requires Node 21+. This is NOT introduced by tree-sitter changes; verify any new test failures are not on this list before claiming a regression.
- TypeScript typecheck for the monorepo workspace: `npx tsc -p packages/langium-cli` (no output means success).
- Run langium-cli tests in isolation: `npx vitest run packages/langium-cli`.
- Tree-sitter artifacts live in `packages/langium-cli/src/grammar-parser/lang/` (grammar.js, langium-grammar.wasm, generated C parser sources, the commonjs `package.json` override, tree-sitter.json). The parent `src/grammar-parser/` is ESM and contains the TypeScript sources (`grammar-parser.ts`, `grammar-queries.ts`). Do NOT put any `.ts` files inside `lang/` — they would inherit `type: "commonjs"` and break under `verbatimModuleSyntax`.
- The `lang/` directory needs its own minimal `package.json` with `"type": "commonjs"` because langium-cli's package.json declares `"type": "module"` and tree-sitter's `grammar.js` uses CommonJS `module.exports`.
- Tree-sitter's regex engine (`regex-syntax` crate) does NOT support look-around (`(?=...)`, `(?!...)`, etc). When porting a Langium regex into grammar.js, rewrite lookaheads as character-class enumeration inside `token(seq(...))`.
- `tree-sitter generate` writes its output to the CWD's `src/`, NOT relative to the grammar.js argument. Always `cd src/grammar-parser/lang && tree-sitter generate` (matches the build:grammar-wasm npm script). Running it from `packages/langium-cli` with the path arg dumps output in the wrong place.
- `tree-sitter generate` is hardcoded to find a file literally named `grammar.js` in CWD; passing a path like `grammar.cjs` or `./other-name.js` does NOT work even if Node would otherwise resolve it.
- `tree-sitter build --wasm` requires either Docker with platform-matching emsdk image or a local `emcc`. The bundled docker fallback uses `emscripten/emsdk:3.1.64` which is amd64-only; on arm64 hosts install emscripten locally (`apt-get install emscripten` on Ubuntu, gives 3.1.69 which works fine).
- web-tree-sitter v0.26+ uses NAMED exports (`import { Parser, Language } from 'web-tree-sitter'`) and `Language.load(...)` is a static method on `Language`, not on `Parser.Language`. The plan's smoke-test snippet is for the v0.20 API.
- web-tree-sitter v0.26 has no `SyntaxNode` export — the class is `Node`. Re-export it under a `SyntaxNode` alias from `grammar-parser.ts` if downstream code expects that name.
- `namedChildren` in web-tree-sitter v0.26 is typed as `(SyntaxNode | null)[]` (allows nulls in error recovery scenarios). When filtering, use a type predicate `(c): c is SyntaxNode => c?.type === '…'` and inside recursion guard with `if (!child) continue;` — TypeScript's `verbatimModuleSyntax` build won't tolerate `node.namedChildren.some(predicate)` when predicate doesn't accept nullable.
- In grammar.js, `interface_decl` supertypes are written as `field('super_type', $.ID)` repeated. `iface.childForFieldName('super_type')` returns ONLY the first super_type — to get all of them, iterate `iface.namedChildren` and filter for `n.type === 'ID' && n !== childForFieldName('name')`. Same pattern for any field declared `repeat(field(...))`.
- Generator rewrites that take `ParsedGrammarSet` cannot remove their old `Grammar`-based exports while `generate.ts` still imports them. The transitional pattern: copy the OLD generator file to `<name>-legacy.ts`, point `generate.ts` at the legacy copy, then replace the original with the new SyntaxNode-based implementation. The legacy file can be deleted in US-047/US-048 when generate.ts switches over. This keeps each per-generator story self-contained and typecheck-clean.
- The plan's verbatim `mapFieldType(typeText, isRef)` only handles primitive type names — for an assignment `name=ID` (where ID is a terminal), `f.type` is `"ID"` and the function returns `"ID"`, but the AC expects `name: string`. Fix by extending `mapFieldType` to accept the `set`, call `resolveRuleRef(typeText, set)`, and treat any matched `terminal_rule` as `string` (or its declared `returns` primitive). Same trick handles parser-rules with `returns string`/`number`/etc.
- The plan's verbatim optional logic `f.operator === '=' || f.operator === '?=' ? '?' : ''` is wrong — it makes every `=` field optional, but the AC for `name=ID` expects `name: string` (no `?`). Only `?=` should produce optional fields. Future generator rewrites must keep this corrected operator-mapping (`'?=' → '?'` only; `'+=' → '[]'`).
- `LangiumConfig.importExtension` is optional (`?: string`). Generators that interpolate it into import paths (`from './ast${config.importExtension}'`) must null-coalesce first (`const importExtension = config.importExtension ?? ''`); otherwise template literals embed the string `"undefined"` and produce broken imports like `from './astundefined'`. Affects every generator that emits TypeScript imports (ast, module, types).
- Per-generator legacy-shim pattern (US-039, US-040): when rewriting a generator to take `ParsedGrammarSet`, copy the OLD generator file verbatim to `<name>-legacy.ts`, point `generate.ts` AND the OLD test file (`<name>.test.ts`) at the legacy copy, then replace the original with the new SyntaxNode-based implementation. The new test lives in a separate file (e.g., `types-generator.test.ts` per the plan's task layout). Both old and new contracts stay under test through the transition; the legacy file is deleted in US-047/US-048.
