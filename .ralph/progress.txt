- **Learnings for future iterations:**
  - **The langium type-checker rejects widening assignments.** When a grammar assignment writes `field=Associativity` (a string-typed rule), the explicit type definition in `langium-types.langium` MUST be exactly `field?: Associativity` — declaring `field?: "left" | "right" | "none"` produces `The assigned type 'Associativity' is not compatible with the declared property 'precAssoc' of type '"left" | "none" | "right"'.` The widening direction (subtype → supertype) is NOT allowed; the declared type must equal the inferred RHS type. Workarounds: (a) match the rule type exactly (what I did), (b) define a new string-typed rule that matches the wider union and use that on the grammar side, (c) accept the field as inferred-only (don't declare in langium-types). Option (a) is simplest when the AC's wider type is just for documentation — `undefined` covers the missing case naturally.
  - **`{Action} keyword (...)? more+=...` forces an AST node.** This is the canonical pattern for "prefix annotation that needs to land on a node". The `{Group}` action creates a Group node BEFORE any field is assigned, ensuring prec/precAssoc have a target even if the rest of the rule produces only one element (which would otherwise skip the implicit `{Group.elements+=current}` action). Use this whenever the annotation is mandatory but the body might collapse to a single token.
  - **`.left`/`.right` after a keyword is just `.` + identifier.** The `.` is already a Langium grammar keyword (from Wildcard). Writing `@prec.left(1)` doesn't need a new compound keyword — the lexer tokenizes it as `@prec`, `.`, `left`, `(`, `1`, `)` and the parser consumes them in sequence. This is preferable to defining `@prec.left` and `@prec.right` as separate keywords because (a) it reuses existing Associativity rule, (b) it produces a clean string field via `precAssoc=Associativity`, (c) it scales to future additions like `@prec.nonassoc` if needed.
  - **The AC's left-recursive example is aspirational.** AC says: `'rule E: @prec.left(1) E '+' E | NUM;'`. This is a left-recursive grammar that WON'T parse with Chevrotain's LL(*) — but @prec is purely a downstream tree-sitter compiler hint (US-020 will translate it to `prec.left(1, ...)` in grammar.js). For the unit test, write a non-recursive grammar that exercises the same SYNTACTIC shape (annotation + multi-token alternative + alternation). Don't try to make the test grammar runnable.
  - **The `prec/precAssoc` fields land on `Group`, NOT on a new node type.** Per AC "Generated AST node for the annotated element has prec?: number and precAssoc?: ..." — this could mean a new node type, but the simpler choice is to extend Group (the existing element-list node). Future grammars compiling to tree-sitter will read these fields off the Group (e.g. `tree-sitter-compiler` walks `def.elements` and wraps with `prec.left(group.prec, ...)` when `group.prec !== undefined`).
  - **Adding keywords with `@` prefix doesn't conflict with the `@` keyword in ReferenceType.** The langium grammar already uses `@` alone (in `[@AbstractType]` cross-reference syntax) and `@word` (US-016). Adding `@prec` is safe because longest-match lexing prefers the longer keyword. The risk: a user grammar with a type literally named `prec` and written as `@prec` would now lex as the `@prec` keyword instead of `@` + `prec`. In practice no one names types `prec` or `word`, so this risk is theoretical.
  - **For US-018 (`conflicts` top-level declaration)** — `conflicts` IS a starting-keyword candidate (it appears at the Grammar top level alongside `grammar`, `import`, etc.). That story WILL need to update the `expectedItems` list in `packages/langium/test/lsp/completion-provider.test.ts` ("Should find starting rule"). Same as US-016 had to do for `@word` (which is reachable via TerminalRule → AbstractRule → Grammar entry).

Signature: `getFoldingRanges(tree: SyntaxNode): FoldingRange[]`. Algorithm: a recursive `walk(node, result)` visits every child; on each visit, if `node.isNamed === true` AND `node.endPosition.row > node.startPosition.row`, it pushes `{ startLine: node.startPosition.row, endLine: node.endPosition.row }`. The walker tolerates `null` entries in `node.children` (the web-tree-sitter `Node.children` array can technically include nulls).

- **Learnings for future iterations:**
  - The folding provider is the *first* tree-sitter LSP provider that does NOT take a `DocumentIndex`. It walks the tree directly. The contract is: any consumer that has a `SyntaxNode` (the parsed tree-sitter root) can produce folding ranges without consulting the index. The aggregator/adapter layer (TBD with US-024+) will need to either (a) keep a per-document map of `{ index: DocumentIndex, tree: SyntaxNode }` so it can dispatch to both index-based and tree-based providers, or (b) cache the tree on the `DocumentIndex` itself. ## Codebase Patterns
- DI services: services are added to `packages/langium/src/services.ts` (LangiumDefaultCoreServices) and wired in `packages/langium/src/default-module.ts` via factory functions `(services) => new Default...(services)`.
- Generated services use the `LangiumGeneratedCoreServices` type — make new generated fields optional for backwards compatibility.
- Public exports go through barrel files: e.g. `packages/langium/src/parser/index.ts` re-exports each parser sub-module.
- File header: every source file under `packages/langium/src/` must include the Eclipse copyright header (enforced by eslint-plugin-header).
- web-tree-sitter is at v0.26.x and uses `Parser.init()` (static, returns `Promise<void>`) and `Language.load(path)` (static, returns `Promise<Language>`).
- Tests use vitest, but `npx vitest run ...` currently fails in this sandbox due to a missing rolldown native binding. This is a pre-existing environment issue, not caused by changes.
- `npm install` at the workspace root currently fails because `packages/langium-web/package.json` has a `file:../../../monaco-languageclient/packages/client` dependency that does not exist in this sandbox. Install is therefore skipped; deps that are already in node_modules continue to work for build/typecheck.
- Build/typecheck commands that work: `npx tsc --noEmit` (from a package dir) or `npx tsc -b tsconfig.build.json` (from the repo root).
- Lint command that works for changed files: `npx eslint <files>`.
- Test fixtures (non-`*.test.ts` files) under `packages/langium/test/fixtures/` are NOT picked up by vitest (`include: ['**/test/**/*.test.ts']`) and NOT linted (eslint config only matches `*.ts`/`*.tsx` under `src/` and `test/`). Tree-sitter `grammar.js` fixtures live there safely.
- Tree-sitter `grammar.js` files are JS modules that expect `grammar`, `seq`, `choice`, `field`, `prec`, `prec.left`, `prec.right`, `repeat`, `repeat1`, `optional`, `token` as globals at runtime (provided by the tree-sitter CLI sandbox). To smoke-test loading without the real CLI, eval the file in a `vm` context with stubbed globals.
- Test files under `packages/langium/test/fixtures/` are picked up by vitest as long as they end in `.test.ts`. Plain fixture data (`metadata.ts`, `grammar.js`) sit alongside `*.test.ts` runners safely.
- When vitest cannot run in the sandbox, smoke-test a pure TS data module by compiling it with `npx tsc --target ES2020 --module ESNext --moduleResolution bundler --rootDir <dir> --outDir /tmp/out <file>` and importing the emitted `.js` from a one-shot node script.
- The name `ReferenceInfo` is overloaded in the public `langium` API: the legacy linker context lives in `packages/langium/src/syntax-tree.ts`, while the new tree-sitter-driven `DocumentIndex` reference entry lives in `packages/langium/src/workspace/document-index.ts`. The new one is the public `ReferenceInfo` exported from `packages/langium/src/index.ts` (because `DocumentIndex.references` references it). Internal consumers that still need the legacy type import it via the relative `../syntax-tree.js` path. When US-027 deletes the CST/linker stack, the legacy type goes with it and the conflict resolves itself.
- TypeScript's `export *` ambiguity between two re-exported barrels can be resolved by adding an explicit `export type { Name } from './path.js'` in the same module — the explicit re-export wins over the wildcards.
- Tree-sitter `Node` API: prefer `childForFieldName('foo')` (returns the named-field child) over index-based lookup. Index-based lookup is wrong when the rule body emits anonymous keyword/punctuation children (e.g. `def NAME = EXPR;` puts the `name` field at index 1, not 0). The web-tree-sitter type is `Node`; this project aliases it to `SyntaxNode` at import sites to match the PRD vocabulary.
- LSP coordinate conversion: tree-sitter `startPosition`/`endPosition` are `{ row, column }` (zero-based); the LSP equivalent is `{ line, character }` (also zero-based). Convert with `{ line: pos.row, character: pos.column }`. The shared helper is `toRange(node)` exported from `packages/langium/src/workspace/index-builder.ts`.
- IndexBuilder walk order: `collectDiagnostics` runs *first* in `walk(node)` (before `if (nodeMeta)`), then `collectDeclaration` + `collectReferences` only when the node has a metadata entry, then recurse children. This ordering matters because ERROR / MISSING nodes have no metadata entry (their `type` is literally `'ERROR'` or the expected token name like `';'`), so any new collector that should fire on them must live outside the `if (nodeMeta)` block.
- Tree-sitter ERROR vs MISSING: ERROR nodes have `type === 'ERROR'`; MISSING nodes have `isMissing === true` and a `type` equal to the expected-but-absent token (e.g. `';'`). Both are surfaced as parse-error diagnostics via the `||` check in `collectDiagnostics`.
- Tree-sitter LSP providers (US-009..015) take a `DocumentIndex` (not a `LangiumDocument`) because the tree-sitter pipeline does not yet flow through the standard `DocumentBuilder`. They are added to `LangiumLSPServices.lsp` as optional fields and registered in `createDefaultLSPModule` with factories that take services-only or no args. Tree-sitter diagnostic providers (parse errors US-009, cross-ref US-010) live together in `packages/langium/src/lsp/tree-sitter-diagnostics-provider.ts`; each returns its own `Diagnostic[]` and a top-level adapter will concatenate them.
- CrossRefDiagnosticsProvider resolution is name-based and per-document only: `index.declarations.has(name)` decides resolved/unresolved. `ReferenceInfo.targetUri` is undefined in the per-document index (US-005) and is not yet consulted. When workspace-wide linking is added, also treat refs with a populated `targetUri` as resolved.
- Tree-sitter LSP providers that share names with existing Chevrotain-era providers (DefinitionProvider, ReferencesProvider, RenameProvider, DocumentSymbolProvider, FoldingRangeProvider) are namespaced with a `TreeSitter` prefix (`TreeSitterDefinitionProvider`, etc.) to avoid collision in the `langium/lsp` barrel. New optional slots are added to `LangiumLSPServices.lsp` alongside the legacy ones; the legacy slots are removed only when US-027 deletes the Chevrotain stack.
- LSP `Location.create` requires a string URI (`DocumentUri`), but `DeclarationInfo.uri` is a langium `URI` instance — always call `.toString()` when handing a `DeclarationInfo` to a `Location` / `LocationLink` constructor.
- `TextDocumentPositionParams` and other `*Params` types live in `vscode-languageserver-protocol`, not `vscode-languageserver-types`. `Location`, `Position`, `Range`, `Diagnostic`, `DiagnosticSeverity` all live in `-types`.
- Tree-sitter Go-to-definition (US-011) range-containment uses inclusive bounds on both ends: a position equal to `range.end` still counts as "inside". This matches the natural "click anywhere on the identifier including its last character" feel. Helper `rangeContains(range, position)` is private to `tree-sitter-definition-provider.ts` and `tree-sitter-references-provider.ts` (duplicated, scoped to two callers); when US-014 adds the third caller, lift it to a shared module under `packages/langium/src/lsp/`.

## 2026-05-03 - US-003
Thread: (ralph autonomous run)
- Created `packages/langium/test/fixtures/arithmetic/grammar.js` — a hand-written tree-sitter grammar for the simplified arithmetic language (Definition, AbstractDefinition supertype, Expression supertype with Addition/Subtraction/Multiplication/Division/Negation/Parenthesized/NumberLiteral/NamedExpression children, plus `Number`, `ID`, `ML_COMMENT`, `SL_COMMENT` terminals).
- Uses `grammar({ name, word: $ => $.ID, extras: $ => [/\s+/, $.ML_COMMENT, $.SL_COMMENT], supertypes: $ => [...], rules })`. Field assignments use `field('name', ...)`. Binary operators use `prec.left(N, ...)` (1 for +/-, 2 for *//), unary minus uses `prec.right(3, ...)`, and `Parenthesized` uses `prec(4, ...)` to demonstrate non-associative `prec()` and ensure paren-grouping commits early. Terminals use `token(/regex/)` with `seq(...)` for multi-part comments.
- Verified: `node --check` accepts the file as valid JS, and a `vm` stub of the tree-sitter DSL (grammar/seq/choice/field/prec/prec.left/prec.right/repeat/token) loads it cleanly and exposes all 16 rules + extras + word + supertypes.
- **Files changed:** `packages/langium/test/fixtures/arithmetic/grammar.js` (new).
- **Quality:** `npx tsc -b tsconfig.build.json` passes; the file is `.js` so it's not in the eslint or tsc include set (intentional — it's a tree-sitter source file, not project source).
- **Learnings for future iterations:**
  - Field names in this fixture are the contract that the metadata fixture (US-004) and compiler (US-022) must match: `Definition` has `name` + `expr`; binary ops have `left` + `right`; `Negation` has `operand`; `Parenthesized` has `expression`; `NumberLiteral` has `value`; `NamedExpression` has `element` (this one is `isRef: true` in metadata).
  - Used `supertypes: [$.AbstractDefinition, $.Expression]` so tree-sitter records the abstract types in `node-types.json` without producing concrete wrapper nodes — `AbstractDefinition: $ => $.Definition` is therefore an alias rather than a structural wrapper.
  - The grammar avoids any feature that the migration checker (US-019) rejects (no UnorderedGroup, no rule parameters, no negated/until tokens, no semantic predicates) — it's the canonical "post-migration" shape.
