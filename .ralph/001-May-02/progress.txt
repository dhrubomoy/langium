- **Learnings for future iterations:**
  - **The `@word` annotation ought to be on arithmetics' ID terminal but isn't.** The arithmetics grammar declares `terminal ID: /[_a-zA-Z][\w_]*/;` without `@word`. Tree-sitter therefore can't disambiguate keywords (`module`, `def`) from identifiers. Tree-sitter's wasm built fine because the language doesn't mix keywords-as-identifiers in any pathological way, but for robust LSP behavior on a real language a `@word` annotation should be added. This is a one-character grammar edit + regen — leaving for a follow-up so this story stays focused on the pipeline activation. The compiler does support `@word` (US-016).
  - **InfixRule lowering convention.** Tree-sitter's idiomatic shape for binary operators is `prec.left/right(N, seq(field('left',$.E), field('operator',OP), field('right',$.E)))` with the rule recursing on itself, plus the base rule as the lowest-precedence terminator. Higher tree-sitter precedence number = tighter binding. Langium's `infix R on B: A > B > C;` orders A (highest priority) first; mapping to tree-sitter is `groups.length - i` for the i-th group. Default associativity is left (Langium and tree-sitter agree). The arithmetics grammar uses 4 precedence groups (`%`, `^`, `*|/`, `+|-`) all left-associative — they map to `prec.left(4)`, `prec.left(3)`, `prec.left(2)`, `prec.left(1)` respectively.
  - **The `parser/` subdir + `package.json` (commonjs) trick is the cleanest way to ship a CJS grammar.js inside an ESM workspace.** Tree-sitter expects `grammar.js` (not `.cjs`) at a fixed path. The CommonJS shim package.json must NOT be in the same directory as TypeScript source files (it breaks `verbatimModuleSyntax` typechecking). Solution: separate the directories. Future tree-sitter outputs from langium-cli follow this layout: `<out>/parser/grammar.js`, `<out>/parser/package.json`, `<out>/metadata.ts`, `<out>/resources/grammar.wasm`.
  - **DocumentBuilder.runCancelable + Parsed phase is the wrong place to run code that should ALSO run for fresh-from-fromString documents.** `runCancelable(documents, DocumentState.Parsed, ...)` skips when `state >= targetState`. Fresh `fromString` documents are already at Parsed. Hooks that need to run in lockstep with parsing belong in the factory's `parseTreeSitter` (or equivalent), not the DocumentBuilder phase callback. US-030's wiring was technically correct for the `update()` path (where state is reset to Changed first) but wrong for the `fromString` path. This iteration moved the IndexBuilder call into the factory; the DocumentBuilder hook is now redundant but harmless (rebuilds idempotently).
  - **`fileURLToPath(import.meta.url)` + `__dirname` dual-mode resolution pattern.** When a TypeScript ESM module gets bundled to CJS by esbuild (target ES2017), `import.meta.url` becomes the empty string — esbuild emits a warning. The cleanest workaround is a runtime branch on `typeof __dirname === 'string'` (true in CJS, undefined in ESM) inside the helper. Type-side: cast through `(globalThis as { __dirname?: string }).__dirname` to avoid declaring `__dirname` globally. Combine with `esbuild`'s `logOverride: { 'empty-import-meta': 'silent' }` to suppress the build-time warning. Pattern reusable for any module that needs to compute a path to a sibling resource.
  - **`langium generate` updates the generated/grammar.ts with US-016's `isWord` field even when the grammar doesn't use `@word`.** Re-running `langium generate` on existing example projects produces a benign diff in `generated/grammar.ts` adding `"isWord": false` to every TerminalRule. Don't be alarmed — it's the regen catching up to the schema change from US-016.

US-033 moves the chevrotain parser into langium-cli; US-034 makes tree-sitter LSP adapters the defaults; US-035 deletes chevrotain from langium runtime; US-036 removes the CstNode hierarchy. ## Codebase Patterns
- DI services: services are added to `packages/langium/src/services.ts` (LangiumDefaultCoreServices) and wired in `packages/langium/src/default-module.ts` via factory functions `(services) => new Default...(services)`.
- Generated services use the `LangiumGeneratedCoreServices` type — make new generated fields optional for backwards compatibility.
- Public exports go through barrel files: e.g. `packages/langium/src/parser/index.ts` re-exports each parser sub-module.
- File header: every source file under `packages/langium/src/` must include the Eclipse copyright header (enforced by eslint-plugin-header).
- web-tree-sitter is at v0.26.x and uses `Parser.init()` (static, returns `Promise<void>`) and `Language.load(path)` (static, returns `Promise<Language>`).
- Tests use vitest, but `npx vitest run ...` currently fails in this sandbox due to a missing rolldown native binding. This is a pre-existing environment issue, not caused by changes.
- `npm install` at the workspace root currently fails because `packages/langium-web/package.json` has a `file:../../../monaco-languageclient/packages/client` dependency that does not exist in this sandbox. Install is therefore skipped; deps that are already in node_modules continue to work for build/typecheck.
- Build/typecheck commands that work: `npx tsc --noEmit` (from a package dir) or `npx tsc -b tsconfig.build.json` (from the repo root).
- Lint command that works for changed files: `npx eslint <files>`.
- Test fixtures (non-`*.test.ts` files) under `packages/langium/test/fixtures/` are NOT picked up by vitest (`include: ['**/test/**/*.test.ts']`) and NOT linted (eslint config only matches `*.ts`/`*.tsx` under `src/` and `test/`). Tree-sitter `grammar.js` fixtures live there safely.
- Tree-sitter `grammar.js` files are JS modules that expect `grammar`, `seq`, `choice`, `field`, `prec`, `prec.left`, `prec.right`, `repeat`, `repeat1`, `optional`, `token` as globals at runtime (provided by the tree-sitter CLI sandbox). - **InfixRule lowering convention for tree-sitter (US-032).** `infix R on Base: A > B > C;` lowers to `R: $ => choice(prec.left(N, seq(field('left',$.R), field('operator', A), field('right',$.R))), prec.left(N-1, ...), ..., $.Base)` with N = number of precedence groups (highest-priority group first in source gets highest N). The base rule is the lowest-precedence alternative so the rule terminates at primary expressions. Field names `left`/`operator`/`right` match the AST shape Langium synthesises in `calculateInfixInterfaces` (NOT `parts`/`operators` — those are the chevrotain intermediate representation). Default associativity is left in both Langium and tree-sitter.
- **ESM/CJS dual-mode path resolution for bundled assets.** When a TypeScript ESM module computes a path to a sibling resource (e.g. grammar.wasm) and gets bundled to CJS via esbuild, `import.meta.url` becomes empty and esbuild emits an `empty-import-meta` warning. Pattern: `function resolveX(): string { const cjsDirname = (globalThis as { __dirname?: string }).__dirname; if (typeof cjsDirname === 'string') return path.resolve(cjsDirname, './rel/path'); return fileURLToPath(new URL('./rel/path', import.meta.url)); }`. Pair with `esbuild`'s `logOverride: { 'empty-import-meta': 'silent' }` and a copy step in `esbuild.mjs` that places the asset at the matching relative path under `out/`. Established in `examples/arithmetics/src/language-server/arithmetics-module.ts` (US-032).

  - **The `conflicts` keyword as a top-level alternative inside the existing `(...)*` repetition is the cleanest design.** I considered (a) a separate top-level rule like `ConflictsDeclaration` that contributes via fragment, (b) a fixed position (before/after rules), or (c) a top-level alternative that intermixes with rules/interfaces/types. The test "two separate conflicts declarations" puts `conflicts: [RuleC, RuleD]` BEFORE the `RuleC: ...` and `RuleD: ...` declarations in the source — the refs still resolve correctly because the scope computation sees all top-level rules regardless of order.   - **The `FeatureName` rule must include any new top-level keyword to preserve its use as an interface attribute name.** `interface`, `entry`, `terminal`, etc. are all in `FeatureName`. If a user wants to write `interface Foo { conflicts: number; }`, the `conflicts` token must be a valid FeatureName even though it's now a keyword. Without this update, the langium-cli would warn "keyword 'conflicts' cannot be used as an attribute name" or similar in any user grammar that has both a `conflicts:` declaration and an interface with a `conflicts` field. This is a defensive update — adding a keyword to FeatureName is essentially free (the FeatureName rule is a literal-or-ID alternation, and adding a literal that's already a keyword has zero ambiguity cost).

Adding `conflicts+=ConflictGroup` in the grammar without declaring `Grammar.conflicts: ConflictGroup[]` in types would generate the field anyway (langium-cli infers it), but the EXPLICIT type definition file is the authoritative source for downstream consumers and is checked by langium's type-system. Same lesson as US-016 (`isWord` on TerminalRule) and US-017 (`prec`/`precAssoc` on Group). Search both files for the AST type you're modifying.
  - **`@AbstractRule` in cross-references resolves to the union type, not a specific subtype.** `AbstractRule = ParserRule | TerminalRule | InfixRule`. So `ConflictGroup.rules: @AbstractRule[]` accepts any kind of rule, not just parser rules. That's the right semantics for tree-sitter conflict resolution (which can involve terminal rules too) but means downstream consumers need to handle all three subtypes. If a future story narrows this to parser rules only, change to `@AbstractParserRule` (which is `ParserRule | InfixRule`).
